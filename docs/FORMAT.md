# mt/7 ファイルの形式

数値はすべて渋谷のサンプル 8 枚（48 メッシュ）で確かめたもの。確認は `scripts/check.py`。整数はリトルエンディアン。

## 取得

```
https://gspe72-ssl.ls.apple.com/mnn_us/<panoid>/<build_id>/mt/7
```

- `<panoid>`: 20 桁にゼロ埋めし、4 桁ずつ `/` で区切る
- `<build_id>`: 10 桁にゼロ埋め
- URL は `streetlevel.lookaround.auth.Authenticator().authenticate_url` で署名する

サイズは 1 枚あたり 55〜102 KB。

## 1. 容器 `MCP4`

| 位置 | 内容 |
|---|---|
| 0x00 | `MCP4` |
| 0x04 | `u16 0` |
| 0x06 | `u16 記録の数`（20） |
| 0x08 | 記録の表: 10 バイトずつ `u16 種類, u32 位置, u32 大きさ` |

記録は表の直後（0x08 + 10 × 20 = 0xd0）から、ファイルの残りをすき間なく、順に覆う。1 ファイル 20 記録で、並びは 種類 5、メッシュ 6 つ、種類 2・3 の組が 6 つ（面 0〜5）、種類 0:

| 種類 | 個数 | 中身 |
|---|---|---|
| 5 | 1 | パノラマの情報（224 バイト、下記） |
| 1 | 6 | 面ごとのメッシュ。`u8 3`、`u32 展開後の大きさ`、続いて LZFSE ストリーム（`bvx2` または `bvxn`） |
| 2 | 6 | 12 バイト: `00`、`u8 面の番号`、`00` × 7、`03 03`、`00`。`03 03` は手元の 30,612 件すべてで同じで、意味は分からない（面の画像は 3 チャンネル 8 ビットの HEIC で、レンズ投影の type は 2） |
| 3 | 6 | 面の低解像度画像。先頭 1 バイト（常に 0）のあとが HEIC（`ftypheic`）。大きさは面 0・2 が 400×336、1・3 が 224×336、4 が 192×192、5 が 384×416 |
| 0 | 1 | 記録と面の対応表（117 バイト）: 0 が 9 バイト、続いて 6 バイトの項目が 18 個。項目の先頭 1 バイトが面の番号、残り 5 バイトは 0。項目 i は種類 5 を除く記録 i + 1 に対応し、値は 0〜5（メッシュ）、0, 0, 1, 1, …, 5, 5（種類 2・3 の組） |

以前は表を 0x12 から読んでいたため、0x08 の 1 つ目の記録（種類 5）を「見出し、意味は未確認」と見ていた。

### 種類 5: パノラマの情報

| 位置 | 内容 |
|---|---|
| 0 | `u16 0` |
| 2 | `u64` パノラマ id（被覆タイルの id と同じ） |
| 10 | `f64 × 3`: パノラマの ECEF 位置。種類 0 の行列の平行移動と同じ値（手元の 5,102 枚すべてで 1 mm 未満） |
| 34 | `f32 0.01`、`u16 180`、`u32 127` |
| 44 | 180 バイト。値 = バイト − 127。**方位 2° ごとの 0〜100 の表を差分で詰めたもの**（下記） |

#### 180 個の値: 方位ごとの表（意味は未確定）

**形**: 先頭が最初の値そのもので、残りは隣との差。累積和 `Q[i] = 値[0] + … + 値[i]`（`pano_info(b)["profile"]`）が方位 2i° の値。

- 手元の 5,094 枚（0 でない値を含むものすべて）で、Q は一度も 0〜100 の外に出ない。最小 0、最大 100 にちょうど届く。差の値は ±15 程度なので、でたらめな列ならこうはならない。
- 一周して戻る: Q[179] − Q[0] の中央値は 0〜1、最大 17。方位 358° から 0° へ戻る 1 段ぶんの差なので、ほかの段の差と同じ大きさになる。差の合計がほぼ 0 になるのもこのため。
- 一定の区間では差が 0 になる。0 でない値が 5〜6 個ずつ続くのは、Q が 10° ほどかけて変わるところ。`f32 0.01` は Q を 0〜1 の割合に直す倍率とみられる。
- 2026 年の撮影の多くは 180 バイトがすべて 0（Q ≡ 0）。金沢 2020 年は全枚に値がある（Q の幅の中央値 44〜62）。

**向き**: 番号 i は、面 0 の中心（u = 0）から u が増える向きに測った方位 2i°。面 0 の局所座標は (x 前, y 右, z 下) なので、上から見て右回り。金沢 2020 年の 120〜250 枚で、方位ごとの特徴とのずれを 0〜358° の 2° 刻みで、向き 2 通りずつ調べると、どの特徴も相関が最大になるのはずれ 0°（±4°）の右回りだった。

**中身として分かっていること**: 「開けている」方位ほど Q が高い。ただし、メッシュから計算できる量とはどれも完全には一致しない。

| 方位の列ごとの量（面の画像の画素にメッシュの距離を重ねて計算） | Q との相関 |
|---|---|
| 仰角 −20° より上で、距離 7 m 以上の画素の割合（仰角の帯と距離のしきい値を総当たりした中で最良） | +0.51 |
| 距離 10 m 未満の画素の割合 | −0.49 |
| 距離 5 m 未満の画素の割合 | −0.47 |
| 地平線より下の明るさ | +0.38 |
| 空の画素の割合 | +0.28 |
| 空との境目の仰角 | −0.28 |

- 隣り合うパノラマ（1.5 m ほど離れる）の差の値どうしの相関は 0.09 しかない。景色に結びついた量なら、もっと似るはず。
- 被覆タイルの `rig_metrics.occlusion_score`（1 枚 4 個）とは、方位を 4 つに分けて Q の平均を比べても対応しない（r = −0.07）。
- 走行速度・加速度・旋回とも、ほぼ相関がない（|r| ≤ 0.24）。

メッシュは単純化されていて、生の距離センサーの値とは違う。Q はそのセンサーの側の量（どの方位がどれだけ見通せたか、など）なのかもしれないが、確かめる手段がない。

パノラマ id の下位の桁は撮影時刻（ミリ秒）で、同じ走行の id の差は撮影時刻の差と一致する。

LZFSE は Apple 公開の汎用圧縮で、`pyliblzfse` で展開できる。展開後の大きさは 1 面 0.9〜14 KB。

## 2. メッシュ = `CHNK` 小区画の並び

各小区画の見出しは 22 バイト: `'CHNK'`、`u16 版 (1)`、`u16 種類`、…、`u32 本体の大きさ`（見出しの +14）。1 メッシュに種類 0・4・5・9・10・11 が 1 つずつ。

### 種類 0: 位置の行列と頂点数

| 位置（メッシュ先頭から） | 内容 |
|---|---|
| 0x16 | `u64` 面の番号 0〜5 |
| 0x1e | `f64 × 16`: 4×4 行列（行優先、最後の行は 0 0 0 1）。局所座標 → 地心座標（ECEF） |
| 0x9e | `u32 V`（頂点数）、`u32 F`（三角形数） |

- 回転部分は誤差 1e-16 で正規直交、行列式 +1。面ごとに 90° ずつ違う
- 平行移動はパノラマの ECEF 位置。6 面で共通。パノラマ間の距離は GPS と 0.2 m 以内で一致（実測の最大差 0.14 m）

### 種類 4: 接続情報（Edgebreaker）

| 位置（本体の中） | 内容 |
|---|---|
| 0 | `u32 F, u32 V, u32 F, u32 0, u32 12, u32 0`（24 バイト） |
| 24 | CLERS 文字列: `C` `L` `E` `R` `S` の ASCII 文字が三角形 1 つにつき 1 文字、F 文字 |
| 24+F | `u32 F, u32 V, u32 1` |

**復元の約束**（48/48 のメッシュで検証済み、実装は `lookaround_mesh/edgebreaker.py`）:

- 各メッシュは位相的に**円盤**。境界の頂点数 b = V − (C の数) = 2V − F − 2（オイラーの関係と一致）。E の数 = S の数 + 1。
- 最初のアクティブループ = 境界。境界の頂点を 0..b−1（ループ順）、C が現れるたびに内側の頂点 b, b+1, … と番号を振る。
- ループをリストで持ち、先頭の辺 (loop[0], loop[1]) をゲートとする。

| 操作 | 3 つ目の頂点 x | 新しいループ |
|---|---|---|
| C | 新しい頂点 | `[x] + loop[1:] + [loop[0]]` |
| L | `loop[-1]` | `[x] + loop[1:-1]` |
| R | `loop[2]` | `[loop[0]] + loop[2:]` |
| S | `loop[k]` | 右 `[x] + loop[1:k]` を先に処理し、左 `[loop[0]] + loop[k:]` を積む |
| E | `loop[2]`（長さ 3） | 積んだループを取り出す |

三角形はどれも `(loop[0], loop[1], x)`。

- S が切り出す長さ k は文字列だけから決まる。分岐の中で C は +1、L と R は −1、入れ子の S は 1 − (切り出す長さ)、E は長さ 3 のループを閉じる。この計算で文字列全体に必要な最初のループの長さが、48/48 のメッシュで境界の頂点数と一致する。
- この約束で復元すると、三角形数・頂点数が一致し、潰れた三角形がなく、どの辺も 2 枚以下の三角形に属し、向きが一貫し、境界の辺がちょうど b 本になる（48/48）。L と R を入れ替えると、これらが全部崩れる。

### 種類 5: 三角形ごとの面番号

`u32 F`、`u32 1`、続いて三角形ごとに 1 バイト（F バイト）。値は（面の番号 + 1）で、1 メッシュの中ではすべて同じ。

### 種類 9: 頂点

| 位置（本体の中） | 内容 |
|---|---|
| 0 | `u32 V` |
| 4 | `f32 0.001`、`f32 0.001`、`f32 1000`（u・v の単位 = 0.001 ラジアン、距離 = 1000 / w m） |
| 16 | `u16 0` |
| 18 | `f64 × 16`: 4×4 行列。地心座標 → 局所（種類 0 の逆で、行が (y, z, x) の順。値の軸の順 (u, v, w) に対応） |
| 146 | 40 バイト、全メッシュで同一: `u16 0, u16 1, f64 1.0, f64 1.0, f64 0.0, f64 0.0, u32 127`。4 つの f64 は種類 10 の投影と同じ位置にあり、ここでは恒等（値は角度のまま）。127 は本体のバイトから引く値 |
| 186 | **本体**: V×3 バイト。値 = バイト − 127。ただし `0xff` は「例外表から次の値を取る」印 |
| 186+3V | **例外表**: `i32` の列。長さは本体の `0xff` の数と一致（48/48） |

実装は `lookaround_mesh/vertices.py`。

#### 値の並び

本体は**軸ごと**に並ぶ: V 個の u、V 個の v、V 個の w。各軸の中は **Apple の頂点番号**の順。

- 内側の頂点: `edgebreaker.decode` と同じ（C の順に b, b+1, …）。
- 境界の頂点: 最初の三角形の角 1（下記）の頂点から、その頂点の扇を回って境界の辺に出て、そこから境界を歩きながら b−1, b−2, …, 0 と振る。`decode` の境界の番号（ループ順 0..b−1）とは向きも起点も違う。先頭が C のメッシュでは、`decode` の j が Apple の (j−1) mod b になる。

#### 座標の組み立て

三角形 w = (a, b, x)（`decode` の出力、x が先端）の角を 3w+0 = x、3w+1 = a、3w+2 = b とし、辺を共有する向かいの角の表を作る。

1. 最初の三角形の 3 頂点は**値そのもの**（予測なし）。
2. 面 0 から始めて、面を取り出すたびに、その面の角 0, 1, 2 の順に、角の向かいの辺の先にある未訪問の面を**スタック**に積む。積んだ時点で訪問済みにする。
3. 面を取り出したとき、その先端（入ってきた辺の向かいの頂点）がまだ決まっていなければ、**積んだ側の面**から平行四辺形で予測し、値を**足す**: `P[k] = P[h] + P[i] − P[j] + 値[Apple 番号 k]`（h, i は共有する辺の両端、j は積んだ側の面の残りの頂点）。

Apple Flyover の C3M 形式の Edgebreaker 変種（[retroplasma/flyover-reverse-engineering](https://github.com/retroplasma/flyover-reverse-engineering) の `edgebreaker.go`）と同じ系統。頂点番号の振り方と「最初の三角形は生の値」は同じだが、mt/7 では値を引かずに足し、頂点を積む時ではなく取り出す時に決める。

#### 座標の意味

面ごとの球面座標（Look Around の面は立方体ではなく、パノラマを経度で 4 つに切った帯と、上下の帽子）:

- u = 経度、v = 緯度（下向きが正）、単位 0.001 ラジアン。局所座標は (x 前, y 横, z 下) = r · (cos v cos u, cos v sin u, sin v)。種類 0 の行列で ECEF に移る
- w = 距離の逆数。距離 r = 1000 / w m。空は w = 0（無限遠）。w は整数なので、奥行きの刻みは距離 r で約 r² / 1000 m（10 m で 0.1 m、20 m で 0.4 m、50 m で 2.5 m）。遠いビルの壁は粗い

面ごとの範囲（渋谷のサンプル 8 枚で共通、差 2 以内）。**範囲は撮影（走行）によって違う**: 金沢 2020 年の側面は v が −1081〜531 で、渋谷 2026 年の −1220〜609 より狭い。決め打ちにせず、メッシュごとの最小・最大から求めること。

| 面 | u | v | 経度の担当 |
|---|---|---|---|
| 0, 2（前・後） | ±1078 | −1220〜609 | ±1016（116.5°）＋重なり |
| 1, 3（横） | ±588 | −1220〜609 | ±554（63.5°）＋重なり |
| 4（空） | ±522 | ±522 | 天頂から 30° |
| 5（地面） | ±1062 | ±1132 | |

#### 面の画像との対応

MCP4 の種類 3 の画像（先頭 1 バイトのあとが HEIC）は、**その面のメッシュの角度の範囲をちょうど覆う**。画素は角度に対して線形で、1 画素およそ 5.3〜5.5 mrad（0.31°）。画像の大きさは範囲に合わせて変わる（渋谷 2026 年の側面は v の幅 1829 mrad で高さ 336 px、金沢 2020 年は 1612 mrad で 304 px）。渋谷のサンプルでは:

| 面 | 画像 | 1 画素あたり u [mrad] | 同 v |
|---|---|---|---|
| 0, 2 | 400×336 | 5.39 | 5.44 |
| 1, 3 | 224×336 | 5.25 | 5.44 |
| 4 | 192×192 | 5.44 | 5.44 |
| 5 | 384×416 | 5.53 | 5.44 |

角度の範囲は種類 10 の投影（下記）にそのまま書いてある。u, v を rad にして `(u·su + ou, v·sv + ov)` が画像の正規化座標 [−1, 1] で、画素の位置は `x = (u·su + ou + 1) / 2 × W`、`y = (v·sv + ov + 1) / 2 × H`。メッシュの最小・最大から `x = (u − u_min) / (u_max − u_min) × W` としても 1% 以内で同じ（`scripts/export_ply.py` などはこちらを使っている）。頂点を画像に重ねると、w > 0 の頂点は建物や地面の上に、w = 0 の頂点は空の側に乗る。`scripts/export_ply.py` はこれで点群に色を付ける。

#### 検証（`scripts/check.py`）

- 48/48 のメッシュで、w ≥ 0、面ごとの範囲が 8 枚で共通。
- 地面: 半径 3 m の地面の点の高さの中央値（カメラ高）が 2.30〜2.32 m（8/8）。平面からの RMS 0.5〜3.4 cm、法線は鉛直から 0.3〜2.2°（人や縁石のある pano4・5 で大きい）。側面の下端（v = 609 = 34.9° 下）の地面は w ≈ 2.30 m / sin 34.9° の逆数 = 248 と予測され、実測の最大 245〜253 と合う。
- 別走行（翌日）のメッシュ面と、pano0 の地面より 1 m 以上上の頂点（20 m 以内、179 点）の距離:

  | 相手 | 中央値 | 25 cm 以内 | 鉛直軸まわりに 90° 回した対照 |
  |---|---|---|---|
  | pano6（1.7 m 先） | 0.25 m | 51% | 中央値 4.5 m、0% |
  | pano7（3.3 m 先） | 0.28 m | 48% | 中央値 3.0 m、1% |
- 隣の面との重なり部分（経度の担当範囲の外）: 同じ方向の点が距離の 2.5% 以内で一致。
- 三角形の約 1.5% は (u, v) 上で裏返る。奥行きの差が大きい三角形に偏っていて（奥行きの逆数の相対的な開きの中央値 0.29、正常な三角形は 0.13）、物陰で折り返す三角形とみられる。予測の誤りなら後続の頂点に誤差が積み上がって範囲を外れるが、48/48 で範囲に収まる。

### 種類 10: 面の投影

174 バイト。

| 位置（本体の中） | 内容 |
|---|---|
| 0 | `u32 1, u16 1, u16 面の番号` |
| 8 | 134 バイト。種類 9 の 16〜150 バイト目と同一（行列など） |
| 142 | `f64 × 4`: 投影 `su, sv, ou, ov`（`lookaround_mesh.projection`） |

角度 [rad] から面の画像の正規化座標 [−1, 1] への写像 `(u·su + ou, v·sv + ov)`。被覆タイルの `camera_metadata` のレンズ投影と同じ値で、`su = 2/fov_s`、`sv = 2/fov_h`、`ov = cy·sv`（`ou` は観測した範囲では常に 0、`cx` も 0）。渋谷のサンプルの 1 枚で 6 面とも被覆タイルの値と一致した。

| 面 | su | sv | ou | ov | 角度の範囲 |
|---|---|---|---|---|---|
| 0, 2 | 0.925992 | 1.091348 | 0 | 0.333333 | u ±61.875°、v −70°〜35° |
| 1, 3 | 1.697653 | 1.091348 | 0 | 0.333333 | u ±33.75° |
| 4 | 1.909859 | 1.909859 | 0 | 0 | ±30° |
| 5 | 0.939275 | 0.881474 | 0 | 0 | u ±61.0°、v ±65.0° |

これは渋谷 2026 年の値。金沢 2020 年は側面の sv = 1.238828、ov = 0.340541（v −62.0°〜30.5°）で、撮影によって v の範囲が違うことと合う。手元の 608 枚（3,648 メッシュ）すべてで、頂点の正規化座標が [−1, 1] に収まり、両端まで 1% 以内に届く。

### 種類 11: 定数

`02`、`f32 0.05`、`01`。全メッシュで同一（手元の 30,612 件）。0.05 の意味は未確定。値が変わらないので、変化と突き合わせて決めることができない。外れた仮説:

- 距離の打ち切り（1 / 0.05 = 20 として、w < 20 つまり 50 m より遠くを空にする）: 空でない頂点の w の最小は 1（1 km）まで出る。
- 三角形の大きさの下限: (u, v) 上の辺の長さは 0 mrad まである（同じ方向で奥行きだけ違う頂点がある）。

## 未解読のまま残っているもの

- 種類 5 の 180 個の値の**意味**（形は上記のとおり解けている）
- 種類 2 の `03 03`
- 種類 11 の `0.05`

最後の 2 つは手元のデータで値が変わらないので、変化と突き合わせて決めることができない。

上の「全ファイルで同じ」という主張は、すべて日本の車の撮影（2020 年と 2026 年）で確かめたもの。

## mt/7 の外

- `mt/` の番号は 7 だけが返る（1 枚で `mt/0`〜`mt/9` を試した）。被覆タイルの各ビルドの `lod_with_textures` も 7。
- 被覆タイル（streetlevel が読む protobuf）にあって、このリポジトリで使っていないもの: `coverage_type`（車・徒歩）、`has_blurs`、`rig_metrics.occlusion_score`（1 枚 4 個）、`revision`。`raw_orientation`・`raw_altitude` は種類 0 の行列と重なる。

### 被覆タイルのフィールド 3（streetlevel の proto にない）

被覆タイルの最上位には、streetlevel が定義していないフィールド 3 がある（金沢のタイルで 14 個、渋谷のタイルで 64 個）。汎用の protobuf の読み方でほどくと、各項目は**場所・向き・大きさを持つ長方形を、近くの 2 枚のパノラマに結びつけたもの**:

| フィールド | 中身 |
|---|---|
| 1 | `u64` id（16 進で `0280e7…`、`02a0b8…` のような値） |
| 2 | 2 つの小項目（番号 4 と 5）。それぞれ `varint` のパノラマ id と姿勢。2 つのパノラマはどちらも同じタイルにあり、撮影時刻の差の中央値は 2〜4 秒 |
| 3 | 番号 1: 姿勢と `f64 × 2`（1.4〜25 m と 2〜5 m。幅と高さとみられる）。番号 2: `varint` の分類（1・2・4・5） |

姿勢は `f64 × 6`: ECEF の x, y, z と角度 3 つ。角度の 1 つ目は経度、2 つ目は −緯度（その地点の東・北・上の向き）で、3 つ目だけが項目ごとに違う（長方形の向きとみられる）。長方形は、結びついたパノラマから 3〜4 m（中央値）のところにある。大きさ（幅 2.5〜6 m、高さ 2〜5 m が多い）からは店の間口や建物の正面のようにも見えるが、画像に重ねて確かめてはいない。

ほかに、ビルドの表（フィールド 4）の番号 4（値は 1）も streetlevel の proto にない。
